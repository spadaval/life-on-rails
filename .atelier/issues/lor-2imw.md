## Goal

The drawer's first tab is quick dial: what Sumeet is likely to want right now, replacing Recent and Frequent, which duplicated each other. It shows a card for what's next from LoR, eight apps for this hour, the four people he has talked to most recently, and apps installed in the last three days not yet opened. The mock is `docs/missions/launcher-use/mocks/home-quick-dial.html` (right frame).

## Done when

- [ ] Every launchable app that isn't hidden can be ranked, whether or not a tab lists it. Apps are ranked by a pure, tested function of per-app open counts: how often and how lately each app was opened (the existing decaying weight), multiplied by its affinity for the current hour band and day kind (weekday or weekend), smoothed so an app with few opens isn't ranked by one of them. Tests use fixtures: an app opened every morning ranks first at 8:00 and not at 20:00; a weekend-only app ranks on Saturday and not on Tuesday; an app opened once ranks below a daily one.
- [ ] The counts come from Android's usage events (each app moved to the foreground, LoR's own and the launcher's excepted) as well as launcher taps, read incrementally from a cursor when the drawer opens and kept in the launcher's own file, since Android keeps events only a few days. Work apps, whose events the main profile can't read, count by launcher taps.
- [ ] People: the conversation shortcuts `LauncherApps` gives (as search reads them, cached ones included), newest `ShortcutInfo.lastChangedTimestamp` first, at most one per person (by the shortcut's `Person` key, else its label), changed in the last 14 days, the first four shown with avatar, name and app badge; a tap opens the conversation. Without any, the row is absent. The selection is a pure function, tested with shortcuts of the same person in two apps, an old one and fewer than four.
- [ ] The card shows `/device/home`'s `one` (kicker and text) through `LorReads`, greyed with its time when LoR can't be read, and absent without one; a tap does what the header's tap does.
- [ ] On `T3_Phone_API35` against the test server, with usage generated by opening apps through `agent-device`: screenshots of quick dial at two hours set on the emulator (morning, evening) showing different order, with people and the card present.
- [ ] The spec describes quick dial.
- [ ] `assembleDebug testDebugUnitTest` passes on boat.

## Scope

`home/` (the quick tab, the counts), its tests, the spec. No server change; the card's mock "Directions" button is left out, since `/device/home` carries no event location.

## Context

Mission lor-5qkq. LoR already holds Usage access (`collect/AppUsageCollector.kt` reads the same events). LoR's usage data (Oct 13 to Nov 7) shows real time-of-day patterns: United and Uber in the morning, WhatsApp in the evening, YouTube Music during the day.

## Notes

- 2026-11-09 [decision] Estimate: about 600 changed lines (QuickDial.kt ~200, QuickDialRows.kt ~90, DrawerScreen/HomeStore ~150, tests ~170, spec).
  Reason: The assignment's 500 to 800; written down before the build as implement asks.
- 2026-11-09 [decision] Quick dial's 'how often and how lately' is a count per slot (five hour bands x weekday/weekend) where each open adds 1 and every count halves in 14 days, not LaunchStats' per-launch weight. Score = total x (n_slot + 4u)/(total + 4), u the slot's share of the week's hours.
  Reason: LaunchStats moves every weight by alpha=0.03 per launch. Fed with usage events (well over 100 app changes a day) its half-life is about 23 opens, a few hours, so an app opened every morning has decayed to nothing by evening and the hour weighting has nothing to work with. A time half-life keeps the same idea (often and lately) at any event volume. The strategy lets the orchestrator choose the score's weights.
  Rejected: Reuse LaunchStats' weight fed with usage events (decays too fast)
  Rejected: Tune LaunchStats' alpha down (changes search's tie order too)
- 2026-11-09 [decision] People are deduped by the shortcut's label, not its Person key.
  Reason: ShortcutInfo.getPersons() is a @SystemApi: it is not in the public android.jar (checked with javap on android-37.0), so a launcher can't read the Person. The Done when line's 'else its label' is what applies. The same person in WhatsApp and Messages usually has the same name, which the test covers.
- 2026-11-09 [decision] Emulator check on boat's T3_Phone_API35 with the host's test server forwarded into the VM by 'boat forward --reverse --local 3857', so the app's server_url stays http://10.0.2.2:3857 (the emulator's 10.0.2.2 is the VM's loopback).
  Reason: The local T3_Phone_API35 is still held by another thread's agent-device session (t3-96ff96...), which this thread may not reuse or close. A forward reaches the real test server, so the card is shown from a real /device/home with a pin set on the test database, not faked.
