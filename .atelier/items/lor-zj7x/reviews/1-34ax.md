## Finding 1: Start the four system pages with fictional content in version 1
Recommendation: fix now

`scripts/demo.ts:127` calls `ensureSeed`, which inserts the real `src/db/pages/` bodies and titles into `page_version`. The overwrite at `scripts/demo.ts:317-321` adds version 2 without removing version 1. Consequently the demo database still contains the owner's original `agent`, `me`, `messaging-rules` and `inbox` pages. This defeats the goal that screenshots and prototypes contain only made-up information, and the report's claim that overwriting the seed pages prevents that exposure.

After loading the demo, querying page history showed `me` version 1 with title `Sumeet` and version 2 with title `Me`. Opening `/notes?slug=me&version=1&at=09:00` in the browser displayed the old-version notice and the original owner's name/content. Notes exposes those versions through its ordinary History links. Create these pages with demo content from their first version, rather than leaving real seed bodies in history, and check all four histories as well as their heads.

## Finding 2: Restore the proposal and label when undoing a timer variant
Recommendation: fix now

`src/server/demo.ts:75-77` records only the newly started timer block for undo. Starting that timer also re-syncs fill, which deletes/replaces overlapping phone and place blocks; the old blocks' proposals are deleted with them. `undo` at `src/server/demo.ts:56-62` deletes the timer and regenerates fill but cannot reconstruct the agent's original proposal or label.

Reproduction on a freshly loaded demo: the YouTube/Maps phone block has the pending agent proposal for `Portuguese lesson`. Request `/device/state?data=running&at=15:00`, then `/device/state?data=base&at=15:00`. The number of pending agent proposals goes from 1 to 0, and the recreated `YouTube 30m · Maps 8m` block has no intent. Thus visiting the documented running state permanently removes the documented suggestion-to-confirm state until the entire demo is reloaded. The variant test checks only the restored block count, so it passes despite this loss. Preserve and restore the affected base labels/proposals and test the actual base state after a round trip.

## Finding 3: Format the fixed sidebar time in LoR's timezone on both server and client
Recommendation: fix now

`src/routes/__root.tsx:101-103` formats the fixed instant without a `timeZone`, so SSR uses the host's timezone rather than `LOR_TZ`. The `suppressHydrationWarning` at line 54 leaves that server text in place when the browser initially formats it differently, and the fixed clock disables the interval that would otherwise redraw it.

With both LoR and the test browser set to `America/Los_Angeles` on this New York host, `/?at=09:00` correctly showed the next event at 09:30 in 30 minutes, but the sidebar stayed at `Tue 17 Nov · 12:00` before and after the 21-second wait. The same independent browser check returned sidebar times 03:05, 18:00 and the next day's 00:30 for `at=00:05`, `15:00` and `21:30`. Browser `Intl.DateTimeFormat().resolvedOptions().timeZone` confirmed Los Angeles. This makes the fixed-clock check fail and draws inconsistent screen states. Give the sidebar the configured timezone and use it explicitly for both renders.

## Finding 4: Preserve seconds in local ISO clock values
Recommendation: defer

`src/server/clock.ts:34-35` accepts a local timestamp with seconds but passes only its `HH:MM` capture to `localTimeOnDay`. For example, `parseClock("2026-11-17T09:00:47", "America/Los_Angeles", ...)` returns `2026-11-17T17:00:00.000Z`, silently discarding 47 seconds. Offset-bearing ISO values preserve their seconds. This is outside the four minute-aligned demonstration times, so it need not block them, but the advertised ISO clock input should preserve the instant or explicitly reject unsupported precision.
