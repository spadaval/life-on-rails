## Finding 4: Compare numeric listener ports and account for URL defaults
Recommendation: fix now

`cli/lor.mjs:137,151` and `scripts/ui-check.mjs:23` compare raw configured strings with `URL.port`. The server instead converts configured ports with `Number` (`scripts/serve.mjs:38-39`), while URL parsing normalizes leading zeroes and removes default ports. These checks therefore miss valid configured production listeners: an env file with `LOR_PORT=04000` means listener 4000 but is compared as `"04000"` against `"4000"`; with `LOR_PORT=80`, `new URL("http://127.0.0.1:80").port` is empty and misses `"80"`.

I reproduced both cases using a fake token and intercepted fetch/browser startup. For each fake env file, invoking the source CLI with `LOR_URL=http://127.0.0.1:<numeric port>` reached `POST /api/v1/intents` and exited 0. Running ui-check with that base reached the browser-start interception rather than exiting 3. The control env file with `LOR_PORT=4000` correctly produced exits 6 and 3. No network request or browser ran.

Normalize configured ports numerically, compare against the effective URL port (including its protocol default), and add interception-based regression cases. `scripts/shots.mjs:83-86` already applies this comparison. Otherwise the configured-listener Done when requirements still permit writes to real LoR under these supported configurations.
