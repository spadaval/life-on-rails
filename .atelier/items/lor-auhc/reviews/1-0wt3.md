## Finding 1: Do not stop looking for a fitting task after the first 50 tasks
Recommendation: fix now

`src/server/today.ts:314` limits the candidate query to 50 rows before `assignGapTasks` checks which tasks fit. A later task can fit even when every task returned by the query is too long, so the strip silently disappears despite having both a usable gap and an eligible task. This fails the requirement to offer the next gap with a task that fits it.

Reproduced through `getToday` on `life_on_rails_test`: created 50 active owner tasks, due first, each estimated at 20 hours, followed by a 15-minute task due later. At noon on a calendar-free day ending at 22:00, the result is one 600-minute gap with `fits: null`. The 15-minute task should be offered. Remove the arbitrary candidate limit, or apply fit eligibility before a limit in a way that preserves due ordering and distinct assignments across gaps. Add coverage at the query boundary; the pure assignment tests cannot detect this truncation.

## Finding 2: Escape does not dismiss the visible legend
Recommendation: defer

`src/routes/index.tsx:393` sets `open` to false on Escape, but the hover and focus selectors at line 401 continue displaying the legend. The Report says Escape closes it, which the implementation does not do. In Chrome, focus the help button with the keyboard, press Enter, then Escape: `aria-expanded` becomes `false` while the legend remains visible because `:focus-visible` still matches. A second keyboard activation also cannot hide it while focus remains. Hover likewise defeats Escape.

Use a dismissal state that suppresses the automatic hover/focus display until the next appropriate interaction, and test Escape with focus/pointer retained on the trigger. This can be deferred because moving focus or the pointer away dismisses the hint and the required reveal interactions work, but the Report should not claim Escape currently closes it.
